Quick Strategy Panel — design prototype

Clickable mock of the proposed fast path. Nothing here talks to a server; the price is a simulated random walk so the distance-to-trigger moves like it would in a real session. Edit this file, reload, review — before any Kotlin is written.

Simulate state

Tap the rail chips, the BID/ASK blocks, the steppers, SET, ARM and PLACE — they all behave as proposed.

The problem being solved

TodayTaps
Ladder: ॐ → Strategies → ladder → edit → APPLY → arm → confirm → back ×2~10
Rider: ॐ → Strategies → rider → scroll → PLACE → confirm~6
The rider is the stronger case: its suggestion expires with its M5 bar — the app already force-closes the confirm dialog when the card changes underneath you. Six taps to reach a perishable suggestion is the bug.
Worse than the tap count: Settings hides the price. You set a trigger blind, then return to find the market moved. Everything below exists to keep price and trigger on screen together.

1 · One icon, no rail — decided

The entry point is a single ⚡ icon in the top bar, next to the ॐ. There is no rail row at all, so the positions grid loses zero pixels.

This matters more than it looks: in the stacked layouts the positions grid is the only weight(1f) child, so any fixed row inserted steals height directly from it — and that chrome was already trimmed once to feed the grid.

The icon still has to carry state, or you would have to open the panel to learn anything:

  • dot colour — grey idle · amber armed (paper) · red armed (LIVE) · green rider card waiting
  • when armed it shows the distance inline (⚡ ● −8.45) — the number you are otherwise computing in your head
One icon must serve several engines, so the panel carries tabs (LADDER · RIDER), each with its own state dot. That is also how the straddle is added later — one more tab, no new chrome. Tapping ⚡ opens whichever engine is most urgent: a perishable rider card outranks an armed ladder.

2 · Overlay, not insert

The panel slides over the positions grid. Price, BUY/SELL and the CLOSE row never move.

Button position carries the function here; muscle memory on CLOSE ALL matters more than the panel does. A layout that shifts under a moving market is a hazard, not a feature.

3 · Why not swipe-from-the-edge

Two hard collisions.
① SwipeToDismissBox in the positions list already owns horizontal swipe (EndToStart closes a position) — a panel gesture would sit on top of a destructive action.
② The screen edges belong to the system back gesture (portrait-locked, no exclusion rects).
So: keep the panel, drop the gesture. Tap targets only.

4 · Stop typing prices

Typing 4138 while the market moves is the real bottleneck. Instead: @BID / @ASK seed the trigger in one tap (the BID/ASK blocks themselves are tappable while the panel is open — dashed outline), then ±0.1 / ±1 nudges. The live distance-to-trigger is shown, because that is the number you are currently computing in your head.

5 · SET and ARM stay separate

The existing APPLY deliberately sends enabled = null — “setting a level can never ARM the engine as a side effect.” Merging them into one fast button would destroy that invariant, so the panel keeps two. ARM routes through the existing confirm dialog, which reads the applied server trigger and warns when it is already crossed (try arming a BUY with a trigger below price).

6 · Reuse, don't reinvent

  • setStrategy(id, enabled, params) — one request; enabled=null tunes only.
  • placeRiderCard() — already converts absolute prices → point distances (the unit trap that shipped a bug once).
  • GuardBar's draft-state + resync pattern — mandatory, or a 5 Hz snapshot wipes the trigger field mid-type.
  • Existing AlertDialogs for arm / paper-off / place.

7 · Two-stage: peek, then expand — decided

The panel opens as a peek carrying only what is needed to act:

PeekExpanded (tap ⌃)
Ladderside · trigger · @BID/@ASK · steppers · distance · SET/ARM + lot, target, retrace, max, paper/live
Riderside · lot · entry · PLACE + SL, TP, reason, paper record
Peek keeps the positions grid mostly visible, which matters because the grid is what tells you whether the last rung actually filled. Expanding is one tap and is only needed when you are changing the setup rather than acting on it.
